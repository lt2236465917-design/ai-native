# Solo 与 Team 采用配置

本文件是 `[ADAPTATION]`。它帮助 Skill 根据组织规模减少或增加仪式，不把 Team 的流程强行套到 Solo 开发者。

## Solo profile

### 适用信号

- 一个主要开发者同时承担产品、工程和发布判断；
- 一个仓库或一个小型产品；
- 可接受轻量 artifact 和单人 gate；
- 没有专门的平台、QA 或合规团队。

### 最小配置

- 一个 `intent/` 或 `docs/intent/` 目录；
- 根 `AGENTS.md`，只写稳定命令、架构事实和验证要求；
- `intent.md`、`spec.md`、`plan.md` 三份短产物；
- 一个明确的“自己批准”记录，仍要写日期和理由；
- 一个可重复的 test/build 命令；
- 生产发布前至少有一次显式自审和可回滚点。

### 不应强加

- 多人签批、每阶段会议或复杂 RACI；
- 为了模拟企业治理而维护大量重复 adapter；
- 没有实际收益的全量指标平台。

## Team profile

### 适用信号

- 两名或以上贡献者；
- 产品、设计、工程、QA、发布或运维之间存在交接；
- PR、分支和 CI 已经是团队工作入口；
- 需要共享工程上下文和责任边界。

### 最小配置

- 根 `AGENTS.md` + 必要的子目录上下文；
- 每个 artifact 的 owner、reviewer、状态和版本控制位置；
- 产品/工程/安全或发布的高风险 gate；
- Skill、hook、CI 和权限的控制层分工；
- PR review findings 和 incident record 能回写到链条；
- 试点前后有基线和复盘日期。

### 不应假设

- 所有成员使用同一个 Agent 或同一个 IDE；
- 所有 Copilot/Claude/Gemini surface 具有相同的指令加载能力；
- 绿灯 CI 等于产品验收或合规通过。

### 四人团队的最小角色映射

四人不必对应四个专职岗位，角色可以兼任；但同一个人不应在高风险 gate 上既提出决定又独自批准自己的产物。至少明确以下责任：

| 责任 | 可兼任角色 | 最小独立性要求 |
|---|---|---|
| 产品意图与范围 | 产品负责人/发起人 | `intent.md` 的范围和风险不能只由 Agent 决定 |
| 设计与实施计划 | 工程负责人/设计负责人 | `spec.md`、`plan.md` 的技术风险有人复核 |
| 验证与审查 | QA/工程 reviewer | 关键变更至少有一次不由实施者独自完成的复核，或记录补偿控制 |
| 发布与运维 | 发布/值班负责人 | Deploy/Maintain gate 有授权、回滚和观测证据 |

如果四人中有人兼任多个责任，记录兼任关系、冲突缓解和谁拥有最终 gate；不要把“有四个人”自动等同于“四个独立批准人”。

## 风险扩展（不等于 Enterprise 产品）

使用 R0–R3 作为本 Skill 的轻量路由标签：

| 等级 | 例子 | 人工与确定性要求 |
|---|---|---|
| R0 | 本地实验、无真实用户数据 | 可用轻量自审和本地检查 |
| R1 | 内部工具或低风险功能 | 至少一名 reviewer、CI 基线和回滚说明 |
| R2 | 面向客户的常规功能 | 明确产品/工程 gate、发布证据和观测 |
| R3 | 受监管、支付、安全关键或不可逆操作 | 专门责任人、确定性阻断、审计保留和显式发布授权 |

R 标签是 `[ADAPTATION]`，不替代组织已有的风险分类、法律义务或安全标准。必须同时记录用户自述风险、Skill 的建议风险和最终人工决定；低风险描述不能被 Skill 静默升级或降级。Enterprise 需求若涉及 managed settings、身份权限、审计留存或平台集成，只在本 Skill 中做控制映射和待办，不擅自配置生产系统。

## Profile 输出差异

| 输出 | Solo | Team |
|---|---|---|
| Adoption Pack | 1 页基线 + 三份核心 artifact + 自审清单 | 基线、依赖图、角色/门禁矩阵和试点计划 |
| 工程上下文 | 根文件优先，保持短 | 根文件 + 必要的路径层叠文件，记录 owner |
| Gate | 单人明确批准并留痕 | 按风险指定 reviewer/负责人 |
| 度量 | 周期时间、返工、失败测试 | 交接等待、review findings、部署/事故指标 |
